# 계약 일정과 매물 상태

013 추가 마이그레이션을 적용합니다. 기존 계약·고객·사진·RLS는 유지하며 기존 계약 날짜를 일괄 덮어쓰지 않습니다. 날짜가 완성된 기존 체결·진행·정상 종료 계약은 매물 상태 자동 반영에 포함됩니다. 계약일/잔금일이 없는 기존 계약은 보완하기 전까지 자동화에서 제외합니다.

## 화면과 날짜

신규 계약은 ‘체결’이 기본입니다. ‘작성 중’으로 보관한 계약은 매물 상태에 영향을 주지 않습니다. 매매·전세·월세 모두 계약일과 잔금일을 입력합니다. 전월세 등록·수정 화면에서 입주 예정일과 시작일은 제거하고 잔금일을 두 날짜에 함께 저장합니다. DB 트리거도 신규 입력 및 날짜 변경에 동일한 규칙을 적용합니다. 과거 날짜가 서로 다르면 수정 화면에서 잔금일로 통일됨을 안내합니다. 일정 외 메모만 DB에서 수정하는 경우 과거 날짜를 변경하지 않습니다.

‘1년 (12개월)’, ‘2년 (24개월)’을 선택하면 잔금일을 기준으로 기간의 마지막 날을 종료일에 채웁니다. 예: 2026-11-01부터 1년 → 2027-10-31. 종료일 당일도 임대차 기간에 포함하므로 그날 시작하는 다른 활성 계약은 중복 경고 대상이며, 갱신은 다음 날부터 제안합니다. 월말·윤년은 해당 월의 마지막 유효 날짜를 사용합니다. 종료일을 직접 수정하면 선택을 ‘직접 입력’으로 바꾸며 실제 기간을 년·개월 또는 일수로 표시합니다. 선택한 기간을 유지한 채 잔금일을 바꾸면 종료일도 다시 계산합니다. 갱신 폼은 이전 종료일 다음 날을 잔금일 기본값으로 제안하며 담당자가 수정할 수 있습니다.

## 상태 규칙

한국 날짜(Asia/Seoul)를 기준으로 다음과 같이 저장합니다.

| 일정 | 매물 상태 |
| --- | --- |
| 계약일 전 | 거래 가능 |
| 계약일부터 잔금일 당일까지 | 계약 진행 |
| 잔금일 다음 날부터 | 거래 완료 |

‘체결’, ‘진행 중’, ‘정상 종료’ 상태이면서 계약 유형·계약일·잔금일이 있는 계약을 대상으로 합니다. 작성 중·취소·중도 종료·소프트 삭제 계약은 제외합니다. 여러 유효 계약이 있으면 현재 계약일~잔금일에 해당하는 계약을 우선하고, 그 외에는 계약일·생성일·ID 순으로 가장 최근 계약을 사용합니다. 기간이 겹치는 예외 계약도 이 규칙으로 결정합니다. 유효 계약이 모두 취소되거나 중도 종료되면 거래 가능으로 돌아갑니다. 계약 등록 화면의 수동 매물 상태 선택은 제거했습니다. 기존 API의 선택적 매물 검토 인자는 호환을 위해 유지되지만 예약 실행 시 일정이 다시 우선 적용됩니다.

매물 거래 완료는 임대차 종료와 다릅니다. 잔금이 지나도 계약 상태·임대차 종료일·만기 업무·고객 연락 기록을 자동 종료하지 않습니다. 실제 퇴거 이후 기존 만기 화면에서 재임대를 명시적으로 검토한 계약은 자동화에서 제외하여 검토한 매물 상태를 보존합니다. 이후 새 계약을 등록하면 새 일정이 다시 적용됩니다. 매물 소프트 삭제도 자동화로 복원하지 않습니다.

## 실행과 재처리

```bash
npm ci
bash scripts/start-local.sh
npm run dev
```

로컬 Compose의 `property-scheduler` 컨테이너가 DB 준비 후 60초마다 `private.run_property_contract_schedules()`를 실행합니다. 앱 또는 브라우저가 꺼져 있어도 **Docker와 DB가 실행 중이면** 동작합니다. 날짜 전환 후 반영 지연은 통상 최대 약 1분이며 화면은 새로고침할 때 최신 값을 읽습니다. Docker가 꺼져 있었다면 다시 실행된 다음 현재 날짜로 따라잡습니다.

계약 저장 시에는 트리거가 같은 트랜잭션 안에서 즉시 매물 상태를 반영합니다. 유효하지 않은 당사자·권한·기간 등으로 계약이 실패하면 매물 상태 변경도 함께 롤백됩니다. 직원이 직접 타 담당자 자료를 수정할 수 있는 권한을 추가하지 않았습니다. 자동 상태 변경만 수행하는 제한된 내부 트리거는 같은 매물·사무소의 계약을 검사합니다. 예약 작업은 신뢰하는 서버 측 DB 연결로 실행하며 private 함수·등록부는 public/anon/authenticated/service_role에 실행·조회 권한을 부여하지 않습니다. 서비스 키를 프런트엔드에 넣지 않습니다.

동일 상태는 다시 저장하지 않아 버전·변경 이력이 중복 증가하지 않습니다. 실제 상태 변경은 기존 매물 이력에 기록하며 예약 실행의 행위자는 시스템(null)입니다. 비활성 직원이 기존 담당자인 경우에도 상태 전환은 계속되고, 신규 담당자 지정은 여전히 활성 직원만 허용합니다.

실패한 매물은 SQLSTATE 경고를 남기고 다음 주기에 재시도합니다. 실행 결과에는 processed/failed가 표시됩니다. 여러 예약 실행의 중복은 advisory lock으로 방지합니다. DB 연결 실패도 60초 뒤 재시도하며 컨테이너 재시작 정책을 설정했습니다.

```bash
docker compose --env-file local/.env -f local/compose.yml logs --tail=30 property-scheduler
```

업데이트 시 013 SQL 오류가 있으면 첫 오류를 해결하고 시작 스크립트를 재실행합니다. 데이터를 초기화하거나 볼륨을 지우지 않습니다. 로컬 수동 재처리는 다음 명령으로 가능합니다.

```bash
docker exec estatematch-db psql -U postgres -v ON_ERROR_STOP=1 -c 'select private.run_property_contract_schedules();'
```

별도 Supabase CLI 또는 원격 환경에는 이 Compose 예약 컨테이너가 자동으로 설치되지 않습니다. 향후 배포 시 신뢰하는 서버 예약 작업으로 같은 private 함수를 주기 실행하도록 별도 구성해야 합니다. 원격 배포·유료 서비스 생성은 수행하지 않았습니다.
