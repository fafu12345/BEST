# 016 — 짧은 매물 목록, 건물·호실과 삭제

## 구현한 화면과 입력

- PC는 여섯 열의 짧은 표, 모바일은 작은 카드다. 담당자·최종확인을 목록에서 빼고 거래희망일·거래일정메모·비고를 표시한다. 담당자와 확인 일정 자체는 기존 DB·상세·필터·대시보드에 유지한다. 상세 필터는 PC에서도 접을 수 있다.
- 비고는 기존 상세 설명과 별도인 `properties.remarks`다. 목록에서 빈 칸에 직접 적고 포커스를 옮기거나 Enter로 저장한다. Shift+Enter는 줄바꿈이며 최대 2,000자다. 저장 실패나 동시 수정 충돌을 표시하고 내용을 보존한다.
- 거래 완료 제외 체크박스를 선택하고 검색하면 서버 DB 조건에서 closed를 제외한다. 거래 상태 필터·건물 조건·페이지 이동과 함께 적용된다. 거래 가능은 녹색, 계약 진행은 황색, 거래 완료는 회색, 보류는 보라색이며 글자로도 구분한다.
- 관련 고객이 이미 있으면 기본 화면은 첫 고객의 입력된 정보와 `수정`만 표시한다. 여러 고객은 추가 인원 수를 표시하며 수정/전체 보기로 펼친다. 수정 시 고객 추가·고객정보 수정·연결정보 수정·해제를 제공한다. 다른 직원 담당 고객의 원본을 수정하지 않고도 담당 매물의 관계·출입 비밀번호를 수정할 수 있다.
- 관계는 임대인·임차인·매도인·매수인·거주자·기타 중 선택한다. 고객 자체의 고정 역할이 아니며 해당 매물과의 관계다. 계약 당사자의 법적 역할은 계속 `contract_parties.role`을 사용한다.
- 소유자 성함·연락처는 선택 입력이다. 고객을 자동 중복 생성하지 않는 매물 참고 정보이며 계약 당사자는 기존 고객에서 확인해 연결한다.
- 상가 호실 등록에서는 도로명주소 입력을 제거했다. 건물 보기 등록 시 주소·총층수를 선택 입력하고 대표·관리자가 건물별 화면에서 수정한다. 기존 매물의 주소는 보존하며 새 폼은 건물 주소를 참고한다.

## 삭제와 권한

계약 상세에 `계약 삭제`를 추가했다. 담당자 또는 같은 사무소 대표·관리자가 삭제할 수 있다. 버전을 검사한 뒤 `deleted_at`만 기록하므로 계약 취소·정상 종료·중도 해지와 구별된다. 체결된 계약도 목록에서 숨길 수 있지만 실제 계약 해지나 퇴거를 의미하지 않는다. 사용자 확인문에 이 차이를 표시한다.

당사자·계약서 원본·수납·완료 상담 및 업무·갱신 연결은 삭제하지 않는다. 미완료 계약 업무는 취소한다. 기존 날짜 자동화가 남아 있는 계약을 기준으로 매물 상태를 재계산하므로 담당자는 실제 거래가능 여부를 확인해야 한다. 삭제된 계약의 앱 조회와 계약서 다운로드는 차단한다. 같은 사무소의 과거 DB 기록 조회 범위는 기존 보관 정책을 유지한다.

직원관리의 `직원 삭제`는 소속 직원을 숨기고 active=false, deleted_at을 저장한다. Auth 계정·직원 ID를 물리 삭제하지 않아 외래키와 과거 기록이 유지된다. 이미 로그인된 직원도 기존 active 기반 RLS와 서버 인증 검사에서 업무 접근이 차단된다. 대표·관리자는 기존 담당 자료를 볼 수 있고 필요하면 담당자를 바꿀 수 있다. 자동 인계나 자료 삭제는 하지 않는다.

본인·대표는 삭제할 수 없다. 관리자는 agent만, 대표는 다른 manager와 agent를 삭제할 수 있다. 직접 REST 요청도 DB 트리거와 컬럼 권한·기존 RLS로 검증한다. 삭제된 직원의 클라이언트 복구는 허용하지 않는다. 직원 이름 수정·삭제는 updated_at 충돌을 확인한다. 계약·직원 삭제의 대상과 실제 처리 직원은 기존 감사기록 테이블에 저장하며 원문 개인정보나 출입 비밀번호를 기록하지 않는다.

## 저장 정보로 자동 입력

건물 선택 시 저장된 건물 총층수를 채운다. `등록된 호실 정보 불러오기`는 같은 사무소·건물 ID·동·호실이 일치하는 기존 매물에서 면적·층 정보를 가져온다. 후보 정보가 없으면 직접 입력을 안내하고, 여러 후보의 면적·층 정보가 다르면 409로 충돌을 알려 임의로 선택하지 않는다. 면적은 계산하거나 추정하지 않는다. 불러온 값은 사용자가 수정할 수 있다. 외부 요청·유료 API·실제 개인정보 전송은 추가하지 않았다.

외부 자동화를 위해서는 API 명세에서 다음을 확인해야 한다.

| 정보 | 필요한 식별·검증 |
| --- | --- |
| 건물 총층수 | 정확한 도로명/지번, 건물관리번호 또는 대장 ID, 동별 지상·지하층 구분 |
| 호실 전용면적 | 건물 대장 ID + 동·호실 + 전용/공용 구분, ㎡ 단위, 자료 갱신일 |
| 이름 검색 | 동명 건물·여러 동의 후보를 제시하고 사용자가 주소를 확인 |
| API 운영 | 데이터 제공 범위·이용조건·호출 한도·비용·서버 키 보관·오류 재시도 |

공공데이터의 건축물대장/건축HUB 계열 API 등을 후보로 검토할 수 있으나, 호실별 전유면적을 실제 제공하는지 문서와 샘플 응답을 확인해야 한다. 오피스텔 이름·호실만으로 전용면적을 정확히 계산하거나 이름에서 총층수를 추측하지 않는다. API 키는 채팅이나 클라이언트 코드에 넣지 않고 서버 환경 설정으로 관리한다.

## 후속 영업 설계 반영

### 건물별 호실 관리

지금 구현한 건물별 호실 화면은 건물 주소·총층수와 연결 매물/호실·가격·거래 상태·계약 이력 링크를 30건씩 표시한다. 매물 목록의 건물별 링크로 이동할 수 있다. 거래 완료를 현재 임대 중이나 실제 점유 상태로 단정하지 않는다. 복수 거래·과거 계약이 있는 같은 호실은 별도로 표시한다.

다음 임대현황표에서는 `building_units`를 독립적인 공간 ID로 추가하고 office_id/building_id/동/호실을 고유 키로 한다. 매물은 영업 건, unit은 실제 공간이므로 하나의 unit에 여러 매물·계약을 연결한다. 기존 property ID와 계약 FK는 유지하며 확정된 호실만 추가 매핑한다. 중복·면적 불일치가 있는 자료는 담당자가 확인한 후 합친다. 현재 거주/공실 상태는 실제 입·퇴거 확인에 근거한 별도 상태로 설계한다.

### 임대인·임차인 각각의 연락

현재 만기관리의 연락 등록은 계약 당사자를 선택해 연락 시각·방법·내용·기록자·다음 연락일을 기록하며, 선택한 고객과 이름 스냅샷을 계약 이벤트에 보존한다. 화면 역할을 한국어로 표시해 임대인과 임차인 중 누구에게 연락했는지 구분한다. 기존 180일 업무는 사무소 운영 기준이며 법정 6개월 통지기한을 판정하지 않는다.

후속 확장에서는 계약 전체의 요약 상태와 별개로 `(office_id, contract_id, customer_id)` 단위의 연락 예정일·협의 결과를 관리한다. 기존 이벤트는 이동·삭제하지 않고 당사자별로 필터링한다. 역할은 연락 당시 스냅샷도 남겨 나중에 역할이 바뀌어도 추적한다. 현재 마지막 연락·종합 협의 상태는 계약별 요약이며 양 당사자의 독립적인 최신 상태 화면은 아직 별도 구현하지 않았다.

### 종료 계약에서 두 중개 기회

현재 `contract_followups`의 모집·퇴거·정산·매물 재등록 검토와 `relocation_cases`의 이전 상담·신규 계약 연결을 재사용한다. 원계약을 종료했다고 매물을 자동 공실 또는 고객을 자동 이전 희망으로 바꾸지 않는다. 실제 의사를 담당자가 확인한다.

후속 `brokerage_opportunities`는 같은 원계약으로 `relet`(기존 매물 재임대)와 `relocation`(퇴거 고객 이전) 기회를 각각 연결하도록 설계한다. 각 기회에 사무소·담당자·현재 단계·다음 연락일·연결된 매물/고객/신규 계약을 기록하고, 원계약·기회 종류·고객 기준의 중복 생성을 막는다. 기존 이전 사례와 재임대 검토 기록에 추가 연결하며 원계약과 상담을 유지한다. 실제 합의가 없는데 자동 생성·종료 처리하지 않는다. 별도의 기회 통합 화면·추가 테이블은 이번 작업에 생성하지 않았다.

## 적용

기존 `.env.local`, `local/.env`, Docker 볼륨을 보존한 채 최신 코드에서 `bash scripts/start-local.sh`로 **016 추가 마이그레이션**을 적용한다. Next 서버를 재시작한다. DB reset은 하지 않는다. 테이블 삭제와 기존 업무 데이터 일괄 변경은 없다.
