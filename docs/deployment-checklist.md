# 운영 배포 전 체크리스트

이번 작업은 로컬 가상 자료 검증까지입니다. 클라우드 배포·유료 서비스 가입·실제 고객 데이터 전송은 하지 않았습니다. 아래 수동 운영 항목이 남아 있으므로 “이미 운영 서버가 안전하게 설정됐다”고 해석하지 마세요.

## 실행 위치와 계정

- [ ] 대표 PC에서 운영할지 별도 서버를 사용할지 결정하고 직원의 접속 방법·가동 시간을 확인한다. 현재 API는 루프백 주소이며 사무실 다른 PC 접속을 자동으로 개방하지 않았다.
- [ ] 기존 owner/manager/agent 권한으로 충분한지, 대표만 수정하고 직원은 조회 전용이어야 하는지 확정한다. 조회 전용 역할은 아직 없으므로 agent를 조회 전용 계정으로 안내하지 않는다.
- [ ] 테스트 계정·기본 테스트 비밀번호·가상 seed는 실제 운영과 분리한다. 실제 최초 대표는 신뢰하는 운영자가 생성한다.
- [ ] 초대·서버 승인·활성 소속·담당자 변경·퇴사자 비활성화 절차를 확인한다. 직원의 office_id/role은 클라이언트가 변경할 수 없어야 한다.
- [ ] 실제 서비스라면 HTTPS·안전한 비밀번호·필요한 MFA·관리 계정 접근 제한을 구성한다. 비밀 키는 서버 전용이며 NEXT_PUBLIC_에 넣지 않는다.

## DB와 파일

- [ ] 변경 전 검증된 DB+파일 백업을 만든다. 001~014를 순서대로 적용하고 첫 SQL 오류부터 해결한다. 실패한 마이그레이션을 적용 완료로 임의 표시하지 않는다.
- [ ] 공개 업무 테이블 25개 RLS, 사무소 복합 FK, 담당자 수정 범위, 불변 수납/연결/감사 기록을 재검증한다.
- [ ] 두 번째 사무소의 매물·고객·계약·알림·통계·파일이 노출되지 않는지 실제 권한으로 확인한다.
- [ ] 사진·계약서 버킷을 비공개로 유지하고 원본 보호·다운로드 감사·Storage 권한을 확인한다.
- [ ] 실제 업로드 용량·디스크 잔여 공간·파일 다운로드·필요 보유기간을 확인한다. 실제 개인정보는 필요한 범위만 수집하고 접근을 제한한다.
- [ ] 앱 감사는 고객 앱 조회와 업무 변경/서류 접근 범위다. 직접 REST/SQL 조회 전체에 대한 감사가 필요하면 별도 DB/플랫폼 로그를 구성하고 보관·접근 권한을 결정한다.

## 백업과 장애 복구

- [ ] [백업 안내](backup-recovery.md)에 따라 대표 PC의 자동 작업을 직접 등록하고 즉시 한 번 실행한다. 이번 개발 작업만으로 PC 예약 작업이 등록되지는 않는다.
- [ ] DB뿐 아니라 Auth·Storage 메타데이터, 사진·계약서 파일, 필요한 복구 설정까지 포함되는지 확인한다.
- [ ] 암호화 비밀번호를 별도로 안전하게 보관하고 다른 물리 장치/장소에 완료 백업을 복사한다.
- [ ] 최근 성공 시각·파일 크기·작업 실행 결과·백업 실패/미실행을 확인할 담당자와 주기를 정한다. 외부 실패 알림은 아직 없다.
- [ ] 복구 도구로 새 DB/파일 볼륨에 실제 복원한 뒤 로그인/권한/문서/수납/최신 계약을 확인한다. Windows 작업 등록은 해당 PC에서 검증한다.
- [ ] 허용 가능한 자료 손실 시간(RPO)과 복구 시간(RTO)을 정하고 정기 복구 시험을 예약한다. 일별 백업만으로 무손실을 보장하지 않는다.
- [ ] 전원·디스크 장애, Docker 업데이트/초기화, 계정 탈취 시 연락·중단·복구 절차를 남긴다. 데이터 볼륨을 삭제하는 Docker 초기화/down -v는 피한다.

## 업무와 알림

- [ ] 계약일~잔금일=계약 진행, 잔금일 다음 날=매물 거래 완료를 확인한다. 임대차 계약 종료·만기·퇴거는 별개다.
- [ ] Docker property-scheduler 로그의 processed/failed와 재시도를 확인한다. 별도 서버/Supabase CLI에는 예약 실행을 별도로 구성한다.
- [ ] 계약별 실제 용도·적용 법률·통지 증빙·갱신 이력·특약 확인 항목을 담당자가 검토한다. 180/90/60/30일을 법정 기한으로 설명하지 않는다.
- [ ] 알림 읽음·숨기기는 개인 표시이며 업무 완료가 아님을 교육한다. 앱은 새로고침 기준이며 외부 문자/카카오 발송은 비활성이다.
- [ ] 수납/환불은 실제 발생 건만 입력한다. 기록은 불변이므로 금액·방향·날짜를 확인하고 정정 근거를 메모한다.
- [ ] 다른 매물로 이전 시 새 계약의 고객을 확인하고 연결한다. 기존 계약 종료 여부를 직접 선택하며 중도 종료는 별도로 기록한다. 잘못된 연결을 임의 삭제하는 화면은 제공하지 않는다.
- [ ] 직원이 같은 고객/계약을 동시에 수정했을 때 409 안내 후 새로고침하도록 교육한다.

## 성능·검증·배포

- [ ] 운영과 비슷한 장비에서 대량 데이터/실제 예상 사진 용량으로 다시 측정한다. [로컬 측정값](performance-results.json)은 인터넷 지연·운영 동시 접속·장기간 스트레스 성능 보장이 아니다.
- [ ] PC/모바일에서 목록·검색·계약·알림·수납·이전 연결을 확인한다.
- [ ] `npm run build`, `npm run typecheck`, `npm run lint`, `npm run test:release` 결과와 실패/생략 항목을 확인한다. 테스트는 가상 로컬 환경에서 순서대로 실행한다.
- [ ] 호스팅·요금제·DB/파일 백업 범위·도메인·운영 비용을 승인받은 뒤 배포한다. 실패 시 되돌릴 앱 버전과 DB 호환성을 확인한다.
- [ ] 배포 후 가상 시험 건으로 핵심 흐름을 확인하고 나서 실제 자료를 입력한다. 테스트 스크립트를 실운영 자료가 있는 DB에 무심코 실행하지 않는다.
