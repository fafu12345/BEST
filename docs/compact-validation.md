추가로 빈 업무 스키마에서 과거 매물·고객·계약·상담·매칭 자료를 넣은 일회용 DB에서 016까지 업그레이드했다. 원래 자료 값과 계약 이력을 보존하고 공개 업무 테이블 26개 모두 RLS가 유지되는 회귀 검사가 통과했다. 실제 앱 DB를 reset하지 않았다. Next production build와 ESLint도 통과했다.

## 새 동작 검증

- 계약 삭제는 담당자·대표·관리자만 가능하고 익명·다른 사무소·타 담당자·CSRF·오래된 버전 요청을 차단한다.
- 활성 계약 소프트 삭제 후 계약의 법적 상태는 그대로 남고 계약 당사자 2명, 비공개 계약서, 실제 수납 기록을 보존한다. 삭제 후 상세/API/계약서 다운로드는 404이며 완료 업무 1개를 유지하고 남은 3개 업무는 취소한다. 매물 상태는 남아 있는 계약으로 재계산한다.
- 직원 삭제는 역할·사무소·본인·대표 보호를 DB 직접 요청에서도 검증한다. 삭제한 직원의 기존 세션으로 API는 401, 직접 REST 조회는 0건이며 담당 매물은 남는다. 관리자 삭제는 대표만 가능하다. 계약·직원 삭제 감사로그를 확인했다.
- 상가 건물 주소·총층수와 선택 소유자 정보, 주소 없는 호실 등록, 비고 버전 충돌, 기존 고객의 관계·출입 비밀번호 버전 충돌을 확인했다.
- 호실 불러오기는 정확히 같은 사무소/건물/동/호실의 저장값만 사용한다. 없는 호실·다른 사무소는 404, 저장값 충돌은 409다.
- PC 가상 매물 30개를 만들고 목록 20개/다음 페이지와 건물별 30개 조회를 확인했다. 기본 PC 표의 테스트 행 모두 높이 120px 미만이었다. 네 상태의 색상 클래스와 상태 문구, 완료 제외 필터 유지, 비고 blur 저장·새로고침 유지, 관계 변경을 검사했다.
- 390px 모바일 카드에서 가로 넘침이 없고 관련 고객·일정·비고가 보인다. 대표 계정으로 실제 계약 삭제·직원 삭제 버튼 확인 절차를 거쳐 저장 결과를 검증했다.
- 테스트는 생성한 UUID의 가상 자료만 정리했다. 보관 계약의 불변성을 푸는 앱 기능은 추가하지 않았으며 테스트 종료 정리만 로컬 관리자 세션에서 처리했다.
