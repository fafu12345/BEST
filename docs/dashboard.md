# 6단계 통합 업무 대시보드

로그인 후 `/dashboard`는 매물·계약·만기·고객을 중심으로 업무를 보여 줍니다.
매칭 테이블을 조회하거나 자동 매칭을 실행하지 않으며 기존 매칭 데이터는 삭제하지 않습니다.

## 적용

최신 코드를 받고 기존 `.env.local`, `local/.env`와 Docker 볼륨을 유지한 상태에서 실행합니다.

```bash
npm ci
bash scripts/start-local.sh
npm run dev
```

012 마이그레이션은 011 다음에 적용합니다. 새 테이블을 만들지 않고 매물의 선택형
`next_confirmation_date date`와 조회용 인덱스·RPC를 추가합니다. 공개 업무 테이블은 기존 21개입니다.
기존 매물·계약·고객 값, RLS와 과거 이력은 보존합니다.
ZIP 사용자는 새 폴더에 최신 ZIP을 풀고 설정 파일 두 개를 같은 위치로 복사합니다.

앞 단계에서 `PGRST205` 오류가 있었다면 011 적용 또는 스키마 캐시 갱신이 필요합니다.
`start-local.sh`의 **첫 SQL 오류**부터 확인하세요. 정상 완료 후에도 캐시 오류가 남으면
`docker compose --env-file local/.env -f local/compose.yml restart rest` 후 앱을 재시작합니다.
DB/볼륨 초기화는 하지 않습니다. 일부 조회가 실패하면 다른 조회 결과와 메뉴는 유지하고,
실패한 값은 **조회 불가**로 표시합니다. 오류를 0건으로 바꾸지 않습니다.

## 집계 기준

모든 날짜 경계는 Asia/Seoul입니다. 담당자 필터는 조회 범위이며 권한 경계는 기존 office_id RLS입니다.
대표·관리자는 사무소 전체, 직원은 본인 담당이 기본입니다. 동일 사무소의 다른 담당자/전체로 바꿔 열람할 수 있지만 수정 권한은 늘어나지 않습니다.
계약 일정은 계약 담당자, 이전 업무는 이전 담당자, 일반 고객 일정은 고객 담당자를 기준으로 필터링합니다.

| 수치 | 실제 DB 계산 기준 |
| --- | --- |
| 전체 관리 매물 | deleted_at이 없는 모든 상태의 매물 |
| 거래가능 매물 | 삭제되지 않고 available 상태 |
| 재확인 필요 | 삭제되지 않고 closed가 아니며 재확인 예정일이 오늘 이하 |
| 진행 중 계약 | 삭제되지 않은 signed/active 계약, 매매 포함 |
| 이번 달 신규 계약 | 계약일(기존 계약은 signed_at)이 현재 한국 월에 속하는 signed/active/completed/terminated 계약. 초안·취소 제외 |
| 30·90·180일 만기 | 오늘부터 각 일수까지 **누적·양끝 포함**, 활성 임대차이면서 후속 처리 open |
| 만기 경과 미처리 | 종료일이 오늘보다 이전이며 후속 처리 open인 활성 임대차 |
| 오늘 연락 | 고객·활성 계약·진행 중 이전 건의 오늘 연락 일정에 연결된 삭제되지 않은 고객 ID를 중복 제거 |
| 이전 희망 고객 | 활성 임대차의 이전 희망 결과 또는 접수/검색/현장 확인 중 이전 건에 연결된 고객 ID 중복 제거 |
| 재계약 협의 고객 | 활성 임대차의 ‘계약 연장 희망’이면서 통지·협의 상태가 ‘협의 중’인 고객 ID 중복 제거 |

담당 계약에 다음 연락일만 있고 연락 고객이 정해지지 않았다면 임차인(없으면 기존 연결 고객)을 대상으로 봅니다.
한 고객의 여러 계약/이전 일정이 같은 날이어도 고객 수는 한 명입니다. 목록은 가장 빠른 연락 일정으로 표시합니다.
법인의 여러 담당자가 서로 다른 고객 레코드라면 각각의 고객으로 계산합니다.

만기 캘린더는 선택한 월의 **체결·진행 중 임대차 전체**를 종료일별로 표시합니다.
후속 처리 완료한 원계약도 아직 활성 상태라면 처리 완료 표시와 함께 보입니다.
반면 상단 만기 수치는 ‘후속 처리 open’만 포함합니다. 달력을 다른 월로 이동해도 이번 달 수치·통계는 현재 월 기준입니다.
만기 경과를 계약 종료나 퇴거로 자동 간주하지 않습니다. 법률상 판단은 담당자 확인 대상입니다.

갱신 통계는 contract_renewals.processed_at과 새 계약 담당자를 기준으로 계산합니다.
정상·중도 종료는 해당 월 실제 contract_events 상태 변경을 유형별 계약 ID로 중복 제거합니다.
단순 메모 수정, 만기일 경과, 이력의 created_at을 종료로 추정하지 않습니다.
과거 종료 계약을 최초 입력했지만 종료 처리 시각이 없는 경우 이번 달 종료 통계에 넣지 않습니다.

## 재확인 일정과 우선순위

매물 등록·수정에서 **다음 재확인일**을 지정합니다. 비워 두면 최종 확인 한국 날짜 +30일,
최종 확인이 없다면 등록 한국 날짜를 사용합니다. ‘확인 완료’로 저장하면 최종 확인 시각을 서버에서 갱신합니다.
별도 예정일이 남아 있으면 그 날짜가 우선하므로 원하면 새 날짜를 지정하거나 비웁니다.
기존 담당자/관리자만 저장할 수 있고 별도의 예약 서버나 cron은 필요하지 않습니다.

우선순위는 다음 규칙을 사용합니다.

1. 만기가 지났지만 처리되지 않은 계약.
2. 기한이 지난 만기·후속 업무 및 일반 고객 연락.
3. 오늘 업무·고객 연락과 재확인 대상 매물.
4. 7일 안의 업무 및 일정 미정 일반 업무.

동일 우선순위에서는 날짜, 일정 미정은 마지막, 마지막으로 고유 키 순입니다.
계약 처리와 해당 확인 업무는 별개 행입니다. 담당자별 업무 건수는 이 우선순위 집계 범위와 같습니다.
이후의 전체 만기 업무는 만기관리에서 조회합니다. 고객이 여러 일정에 등장해도 고객 KPI만 중복 제거하며 개별 업무를 합쳐 버리지 않습니다.

## 화면 연결과 데이터 정확성

만기 목록에서 고객·계약·매물·만기 업무로 이동합니다.
매물 상세에는 계약 당사자, 기존 연결 고객, 상담 고객을 중복 제거해 보여 줍니다.
고객 상세의 기존 과거/현재 계약과 상담 이력을 유지하고 이전 희망·진행 이력을 추가합니다.
보관된 고객은 역사적 이름을 표시하고 활성 상세 링크는 제공하지 않습니다.

집계 함수 `dashboard_core`, `dashboard_workflow`와 관련 고객 조회 RPC는 모두 SECURITY INVOKER입니다.
일반 로그인 사용자 세션으로 실행하며 기존 RLS를 그대로 적용합니다. service_role로 업무를 조회하지 않습니다.
인증되지 않은 사용자는 대시보드 API/화면을 사용할 수 없습니다. 다른 사무소 담당자 필터는 거부합니다.

SQL COUNT/DISTINCT로 전체 자료를 집계해 REST의 1,000행 제한에 잘리지 않습니다.
개요 목록은 20건으로 제한하고 이를 화면에 표시하지만 상단 수치는 전체 집계입니다.
우선순위는 각 DB 집계에서 상위 20건을 가져와 두 그룹의 전체 상위 20건을 표시합니다.
캘린더는 선택 월의 전체 계약을 반환합니다. 가짜 수치, 매칭 점수, 임의 예시 자료를 화면 코드에 넣지 않습니다.
`GET /api/dashboard`는 private/no-store이며 매번 실제 DB를 조회합니다. 역할·필터가 바뀐 뒤 이전 사용자 캐시를 재사용하지 않습니다.

## 검증

```bash
npm run test:dashboard
npm run test:dashboard-ui
npm run test:property-migration
npm run test:expiration-migration
npm run typecheck
npm run lint
npm run build
```

API 검사는 실제 DB 자료로 KPI·담당자·사무소 분리·월 경계·고객 중복 제거·종료 및 갱신 통계를 대조합니다.
1,002개 추가 매물로 REST 행 제한과 관계없이 전체 집계가 정확한지 검증하고 자료를 정리합니다.
오류 격리는 실제 정상 집계 응답과 오류를 주입한 조회 모듈 검사로 확인합니다.
브라우저 검사는 PC/모바일, 캘린더, 재확인 일정 저장, 상세 이동, 대표·직원 기본 범위를 확인합니다.
테스트 자료는 가상 자료이며 개발 DB를 초기화하지 않습니다.
