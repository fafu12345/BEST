# 고객관리

로그인 후 대시보드 **고객관리 열기**, 또는 화면 상단 **고객관리**에서 사용한다.

| 경로 | 기능 |
| --- | --- |
| /dashboard/customers | 이름·법인명·전화·이메일 검색, 구분·담당자·연락 일정 필터, 이름·등록·수정·연락일 정렬 |
| /dashboard/customers/new | 개인·법인 등록, 중복 경고, 담당자 지정 |
| /dashboard/customers/[id] | 기본정보·내부 메모·연락 일정·상담 이력·관련 매물 |
| /dashboard/customers/[id]/edit | 수정, 대표·관리자 담당자 변경, 다음 연락일 변경 |
| /dashboard/customers/schedule | 기한 경과 / 앞으로 7일 / 일정 미정 / 전체 연락 일정 |

PC는 표, 모바일은 카드다. 연락 일정·상담 일시는 한국 시간으로 입력·표시하고 DB에는 timestamptz로 저장한다. 자동 연락·외부 알림은 보내지 않는다.

상담에는 일시, 전화/방문/이메일/메시지/기타, 내용과 선택적인 매물을 기록한다. 최근 활성 매물 200건에서 선택할 수 있다. 상담 이력과 중복 제거한 관련 매물 목록은 각각 20건씩 조회한다. 보관된 매물은 과거 상담에 이름과 보관 상태로 남는다.

고객 역할을 임대인·임차인처럼 고정하지 않는다. 4단계에서 매물별 계약과 역할을 연결한다. 고객 상세의 과거·현재 계약에는 모든 당사자 역할의 계약을 표시하고, 이전 customer_id만 있는 계약도 보존해 조회한다. [계약관리 안내](contract-management.md)를 참고한다.

## DB 및 개인정보 처리 기록 화면 제거

006 마이그레이션은 기존 customers의 id, office_id, assigned_staff_id, 연락처·상태·메모를 보존하며 개인/법인 구분, 법인명, 연락일, 소프트 보관·버전·검색 생성 컬럼을 추가했다. consultations는 contact_method를 추가했다. 기존 id는 customer_id, assigned_staff_id는 담당 직원(assigned_to)으로 계속 사용한다.

사용자 요청에 따라 **개인정보 처리 기록 기능은 화면에서 제거했다.** 수집·이용 근거·처리 목적·동의·보유기한 입력란, 상세 표시, 목록 컬럼·정렬 선택·기한 경과 알림을 제공하지 않는다. 신규 등록에도 해당 필드를 요구하지 않는다.

기존 DB 컬럼과 값은 지우지 않고 이전 클라이언트와의 호환을 위해 선택 필드로 유지한다. 현재 화면은 해당 값을 전송하지 않으므로 기존 고객을 수정해도 보존된다. 기존 sort=retention URL은 최근 수정순으로 처리한다. 사업자등록번호·주민등록번호 필드는 수집하지 않는다.

customer_property_links는 consultations의 사무소·고객·매물 ID를 DISTINCT로 조회하는 security_invoker 뷰다. 호출자 RLS를 적용하며 다른 사무소의 연결은 조회할 수 없다.

## 권한과 보관

- 같은 사무소의 활성 직원만 고객과 상담을 조회한다. 비로그인·미등록·비활성 직원 및 다른 사무소는 접근할 수 없다.
- 담당 직원은 자기 고객 수정·보관·상담 등록. 대표·관리자는 사무소 전체와 담당자 지정·변경 가능.
- DB에서도 office_id/id 변경, 다른 사무소·비활성 직원 지정, 일반 직원의 담당자 변경을 차단한다.
- 상담 작성자와 고객 담당자는 별도이며 담당자 변경 후에도 과거 상담의 작성자를 보존한다.
- 변경 API는 동일 출처, 엄격한 입력, 사용자 세션과 RLS를 사용한다. 일반 업무에 service_role을 쓰지 않는다.
- 고객은 deleted_at으로 소프트 보관하며 상담·매칭·계약 FK를 보존한다. authenticated의 고객 하드 삭제·상담 삭제는 금지한다. 보관 후 일반 앱 조회·수정·상담 추가·복원은 차단한다.
- 같은 사무소 DB 감사용 SELECT에는 보관 행이 남는다. 보관은 영구 파기가 아니다.

중복 경고는 이름·법인명·정규화한 전화번호·이메일 기준이다. 동명이인·공동 연락처는 확인 후 별도 등록할 수 있다. 고객 식별·연락처가 바뀌지 않은 수정에는 중복 재확인을 반복하지 않는다.

## API 및 실행

GET/POST /api/customers, GET/PATCH/DELETE /api/customers/[id], GET /api/customers/duplicates, GET/POST /api/customers/[id]/consultations. PATCH는 customer와 version, DELETE는 version을 받는다. 조회는 private/no-store다. 상담 GET API는 최신 100건이며 화면은 페이지로 과거 이력을 탐색한다.

최신 코드로 업데이트하고 기존 서버를 종료한 프로젝트 폴더의 Git Bash에서:

```bash
npm ci
bash scripts/start-local.sh
npm run dev
```

DB reset이나 Docker 볼륨 삭제는 필요하지 않다. 가상 계정으로 `npm run test:customers`, 브라우저 설치 후 `npm run test:customer-ui`를 실행한다. 실제 고객 데이터·외부 연동·클라우드 배포·유료 서비스는 사용하지 않는다.

### 고객 주소 및 선택 삭제 (010)

`202610150010_customer_address_contract_display.sql`은 `customers.address`를 추가합니다.
기존 고객은 빈 주소로 유지하며 최대 500자까지 저장합니다. 고객 등록·수정·목록·상세 및 계약 등록 중 신규 고객 추가에서 사용합니다.
주소도 기존 고객 RLS에 따라 같은 사무소의 인증된 직원만 열람하며, 담당 직원 또는 대표·관리자만 변경합니다.
계약서 작성 화면과 계약 체결 시점의 주소 스냅샷은 후속 구현 대상입니다.

고객 목록과 다음 연락 일정에서 현재 페이지의 삭제 가능 고객을 선택해 일괄 삭제합니다.
PC 표와 모바일 카드의 선택 상태는 공유합니다. 삭제 확인 후 기존 DELETE API를 고객별로 호출하며,
각 고객의 담당 권한·버전을 검사합니다. 일부만 실패하면 성공·실패 건수와 실패 고객명을 표시합니다.
소프트 삭제이므로 고객 원본, 상담 및 과거 계약 연결은 보존됩니다. 개인정보 영구 파기 기능은 아닙니다.

검증: `npm run test:customer-address-selection` (브라우저 실행 파일은 기존 UI 테스트와 동일하게 설정).
