# 7단계 — 알림·통계·실사용 준비

## 적용과 메뉴

기존 데이터에 **014 추가 마이그레이션**을 적용합니다. 테이블을 삭제하거나 기존 고객·매물·계약을 초기화하지 않습니다. 기존 owner·manager·agent 역할과 사무소 RLS를 유지했습니다. 조회 전용 역할은 이번 변경에 포함하지 않았습니다.

```bash
npm ci
bash scripts/start-local.sh
npm run dev
```

ZIP 업데이트 시 기존 `.env.local`, `local/.env`를 보존하세요. SQL ERROR가 나면 첫 오류부터 해결하고 같은 시작 명령을 다시 실행합니다. 볼륨 삭제나 데이터 초기화는 필요하지 않습니다. DB가 누락된 경우 새 화면은 014 업데이트 안내를 표시합니다.

- **알림** `/dashboard/notifications`: 만기 사전 확인, 잔금 예정, 고객 재연락, 이전 상담, 매물 재확인·재임대 검토, 갱신 미처리.
- **통계** `/dashboard/statistics`: 월별 계약·거래유형 비율·매물유형·담당자별 진행, 갱신·종료·이전 전환, 만기·후속 업무 처리율, 약정 보수와 실제 수납·환불.
- **감사기록** `/dashboard/audit`: 대표·관리자만 고객 목록/상세 접근과 매물 변경이력 삭제 기록을 조회합니다.
- **계약 상세**: 약정 중개보수와 실제 수납·환불 원장을 분리했습니다.
- **만기 상세**: 실제 용도·적용 법률·통지 증빙·갱신 이력·퇴거·정산·특약을 계약별로 확인하고 메모합니다.
- **이전 상세**: 다른 매물에 체결한 신규 계약을 검색·연결합니다. 기존 계약의 정상 종료를 함께 처리할지는 담당자가 명시적으로 선택합니다. 중도 종료는 기존 계약 상태 관리에서 별도로 선택합니다.

[PC 알림](screenshots/operations-notifications.png) · [PC 통계](screenshots/operations-statistics.png) · [모바일 통계](screenshots/operations-mobile.png)는 로컬 가상 자료로 촬영한 실제 화면입니다.

## 알림의 의미

알림은 현재 DB 업무를 읽는 `notification_directory` 보안 호출자 뷰와 `operations_notifications` SECURITY INVOKER RPC에서 생성합니다. 알림 생성용 cron이나 외부 발송은 없습니다. 페이지를 새로고침하면 현재 업무에 맞게 다시 계산합니다. 별도의 실시간 푸시·브라우저 배지·웹소켓 구독은 이번 범위에 없습니다.

- 지난 일정부터 앞으로 7일까지 표시합니다. 잔금 알림은 오늘~7일 이후의 예정일이며 실제 잔금 수령 확인을 의미하지 않습니다.
- 미완료 만기·계약 재연락·이전 상담·퇴거 검토는 기존 expiration_tasks를 사용합니다. 완료·취소한 업무는 해당 알림에서 제외합니다.
- 고객의 직접 재연락 일정은 customers.next_contact_at, 매물 재확인은 지정일 또는 기존 30일 확인 주기를 사용합니다.
- 갱신 희망 + 미처리 상태이며 아직 갱신 관계가 없는 계약에 확인 알림을 표시합니다. 예정일은 다음 연락일 또는 임대차 종료일입니다.
- 업무별 원본을 식별하므로 동일 고객의 별개 계약 상담과 고객 일반 연락은 각각 나타날 수 있습니다.
- 담당자/종류/읽음 상태별 검색, 20건 페이지 조회를 제공합니다. 대표·관리자는 전체, 직원은 본인 담당이 기본이며 같은 사무소 안에서 필터를 변경할 수 있습니다.
- 읽음·숨기기는 **현재 직원 계정만의 상태**입니다. 업무 완료나 다른 직원의 확인을 대신하지 않습니다. 원본 업무 일정·버전이 변경되면 다시 확인할 알림이 될 수 있습니다.
- 외부 채널 경계는 `src/lib/operations/shared.ts`의 NoticeChannel로 분리했습니다. 활성 채널은 in_app 하나이며 SMS/Kakao 자격증명·발송 코드·외부 호출은 없습니다. 향후 외부 발송은 수신 동의·재시도·중복 방지·발송 이력을 별도 설계해야 합니다.

180/90/60/30일 및 7일은 **업무 확인 기준**입니다. 법정 갱신·통지기간, 법률 적용, 갱신권·보증금 정산·퇴거 여부를 일률적으로 판단하지 않습니다. 아파트·오피스텔도 실제 주거/업무 사용 형태를 확인합니다. 상가·사무실은 실제 영업·사용 현황과 특약 등 개별 상황을 확인합니다.

## 통계 집계 기준

모든 수치는 실제 SQL 집계입니다. REST 기본 1,000행 제한에 맞춰 잘린 배열을 세지 않습니다. 현재 직원 사무소의 RLS를 적용하며 시작일~종료일을 포함하고 최대 731일(약 24개월) 범위를 조회합니다.

| 항목 | 기준 |
| --- | --- |
| 계약 건수·월별·유형 비율 | 계약일, 기존 계약은 signed_at. 작성 중·취소·소프트 삭제 제외, 정상·중도 종료 계약은 과거 실적에 포함 |
| 직원별 진행 | 선택 기간에 체결한 계약 중 현재 signed/active, 현재 계약 담당자 기준 |
| 매물 유형 | 연결 매물의 현재 유형. 과거 시점의 유형 스냅샷으로 추정하지 않음 |
| 갱신 | contract_renewals.processed_at, 갱신 계약의 현재 담당자 |
| 정상·중도 종료 | contract_events의 실제 상태 전환일(한국 날짜), 계약별·종료 유형별 중복 제거. 최초 가져온 종료 상태를 이번 달 종료로 추정하지 않음 |
| 이전 → 신규 계약 | 실제 relocation_contract_links 연결일, 신규 계약별 중복 제거. 단순히 이전 건 상태를 contracted로 바꾼 것만으로 세지 않음 |
| 업무 처리율 | 선택 기간에 예정된 미취소 expiration_tasks 중 완료 비율. 만기 확인 외 계약 연락·이전·퇴거 후속 업무도 포함 |
| 약정액 | 선택 기간에 체결한 계약의 알려진 brokerage_fee_krw 합계. 미입력 건수 별도 표시 |
| 실제 수납·환불 | contract_payments.paid_on 기준, 계약 체결일이 기간 밖이거나 나중에 취소된 계약의 실제 현금 기록도 포함 |
| 미수·초과 수납 | 선택 기간의 계약별 현재까지 전체 수납-환불을 약정액과 비교. 과거 날짜 당시 잔액을 재구성한 값이 아님 |

현금 원장은 receipt/refund 추가만 허용합니다. 담당자/대표·관리자만 입력하며, 실제 수납일은 미래일을 받을 수 없습니다. 계약 버전과 idempotency_key로 충돌·재전송을 검사합니다. 같은 키의 같은 요청은 같은 결과를 반환하며 내용이 다르면 거절합니다. 환불은 현재 실제 순수납 잔액을 넘지 못합니다. 입력자·계약 이벤트를 보존하고 수정·삭제는 허용하지 않습니다. 잘못된 거래를 취소하려면 반대 방향의 실제 정정 내역을 기록하고 메모에 근거를 남기세요. 법정 영수증·회계·세무 신고를 대신하는 기능은 아닙니다.

## 이전 상담 → 계약 연결

1. 기존 계약의 고객 연락에서 이전 희망을 기록합니다.
2. 이전 건에 희망 조건·수동 후보 매물·다음 연락일을 기록합니다.
3. 다른 매물에 신규 계약을 등록하고 해당 고객을 임차인 또는 매수인으로 연결합니다.
4. 이전 건에서 고객의 계약을 검색하고 신규 계약을 선택합니다.
5. 기존 계약 종료를 확인했다면 명시적으로 정상 종료를 함께 선택합니다. 선택하지 않으면 기존 계약 상태를 유지합니다.

연결/이전 건 상태/선택적 원계약 종료는 한 트랜잭션입니다. 원계약·새 계약·이전 건의 버전과 담당 권한을 확인합니다. 실패하면 모두 롤백합니다. 사무소가 다르거나 같은 매물, 고객이 빠진 신규 계약, 취소·작성 중 계약은 연결하지 못합니다. 연결은 불변이며 두 계약에 감사 이벤트를 남깁니다. 잘못된 연결의 정정 도구는 아직 제공하지 않으므로 연결 전 확인하세요. 새 계약이 취소되면 실적에서 제외하되 관계 이력은 남습니다.

매물 하나의 갱신 체인(previous_contract_id)은 그대로 유지합니다. 다른 매물로 이전한 계약을 그 체인에 억지로 넣지 않고 별도 연결 테이블로 보존합니다.

## 데이터·감사·동시 수정

- 014의 신규 테이블: notification_receipts, contract_payments, relocation_contract_links, access_audit_events. 공개 업무 테이블 총 25개 모두 RLS.
- 사무소 복합 FK, 담당자 변경 보호, 고객·계약 버전 검사는 그대로 유지합니다.
- 계약 당사자에 선택적 customer_version을 추가했습니다. 새로 검색·추가한 고객이 계약 저장 사이 변경되면 409로 알리고 전체 계약 저장을 취소합니다. 이전 API는 버전 생략을 허용하되 저장 트랜잭션에서 고객 행을 잠그고 최신 정보를 참조합니다.
- 이미 연결된 소프트 삭제 고객은 과거 계약에서 유지하고 계약 메모 수정도 가능하게 했습니다. 보관 고객을 신규 계약에 새로 연결하는 것은 금지합니다.
- 매물 가격·월세·거래 상태 이력에 최종 확인·다음 재확인일 변경도 추가 기록합니다. 중복 경고·매물별 과거 계약 조회·검색·소프트 삭제는 기존 기능을 재사용합니다.
- 앱의 고객 목록/상세 접근은 직원·대상 ID·시각만 기록합니다. 로그 저장이 실패하면 해당 고객 응답을 차단하고 업데이트 안내를 표시합니다. 연락처·검색어·개인정보 원문은 별도 접근 로그에 복사하지 않습니다.
- 계약 수정·상담·수납·이전 연결·서류 업로드/다운로드는 기존 contract_events에 기록합니다.
- 사용자 요청으로 기존 매물 변경이력 삭제 기능은 유지하되 삭제 행위는 별도의 불변 접근 로그에 남깁니다. 삭제된 변경이력 내용 자체가 그 로그에 복제되는 것은 아니며 복원은 백업이 필요합니다.
- 직접 인증된 REST/DB 조회 전체를 기록하는 DB 감사 인프라는 이번 범위에 없습니다. 앱 감사만으로 모든 SQL SELECT를 감시한다고 주장하지 않습니다. 운영 때 DB 접속·플랫폼 접근 권한을 제한하고 필요한 DB 감사/로그 보관을 별도 구성하세요.
